КАК РАБОТАЕТ МОНТИРОВАНИЕ DOCKER СОКЕТА

1. ЧТО ТАКОЕ DOCKER СОКЕТ

/var/run/docker.sock - это UNIX-сокет, через который Docker CLI и другие приложения общаются с Docker демоном (dockerd). Это основная точка входа для управления Docker.

Обычно работа выглядит так:
docker ps -> обращается к /var/run/docker.sock -> dockerd -> возвращает список контейнеров


2. ЧТО ПРОИСХОДИТ ПРИ МОНТИРОВАНИИ

Команда -v /var/run/docker.sock:/var/run/docker.sock делает следующее:
- Хост: /var/run/docker.sock (оригинальный сокет)
- Контейнер: /var/run/docker.sock (такой же файл)

В контейнере появляется этот файл, и он является прямой ссылкой на сокет хоста.

Внутри контейнера можно проверить:
ls -la /var/run/docker.sock
# srw-rw---- 1 root root 0 Mar 23 10:00 /var/run/docker.sock


3. СХЕМА РАБОТЫ

Хостовая машина:
  dockerd (Docker демон) <--> /var/run/docker.sock (UNIX socket)
                              ^
                              | монтирование
  Контейнер docker-manager:   |
    /var/run/docker.sock -----+
    Python SDK -> docker.sock
    client.containers.list()

Запрос из контейнера идет через смонтированный сокет напрямую к демону на хосте.


4. ПОЧЕМУ ЭТО РАБОТАЕТ

Docker SDK внутри контейнера по умолчанию ищет сокет по адресу unix:///var/run/docker.sock. Когда этот файл смонтирован:

1. Python SDK открывает /var/run/docker.sock (внутри контейнера)
2. На самом деле это тот же файл, что и на хосте
3. Запрос передается dockerd на хосте
4. dockerd выполняет операцию (запустить/остановить контейнер и т.д.)


5. ПРОВЕРКА НА ПРАКТИКЕ

На хосте:
ps aux | grep dockerd
# root 1234 ... /usr/bin/dockerd

В контейнере:
docker run -v /var/run/docker.sock:/var/run/docker.sock -it alpine sh

# Проверим, что сокет виден
ls -la /var/run/docker.sock
# srw-rw---- 1 root root 0 ... /var/run/docker.sock

# Установим docker CLI в контейнере и проверим
apk add docker-cli
docker ps
# Выведет список контейнеров ХОСТА, не контейнера!


6. ЧТО МОЖНО ДЕЛАТЬ

Управлять любыми контейнерами на хосте
Создавать/удалять образы
Работать с сетями и томами
Смотреть логи всех контейнеров

Пример на Python:
client.containers.run('nginx', detach=True)  # Создаст контейнер на хосте
client.containers.get('some-container').stop()  # Остановит любой контейнер
client.containers.prune()  # Очистит неиспользуемые ресурсы хоста


7. РИСКИ БЕЗОПАСНОСТИ

Это очень мощный, но опасный подход:

- Root доступ: контейнер получает root-доступ к Docker демону
- Эскалация привилегий: из контейнера можно запустить привилегированный контейнер
- Доступ ко всем данным: можно смонтировать любые директории хоста

Пример уязвимости (злоумышленник внутри контейнера может):
client.containers.run(
    'ubuntu',
    volumes={'/': {'bind': '/mnt/host', 'mode': 'rw'}},
    command=['chroot', '/mnt/host', 'rm', '-rf', '--no-preserve-root', '/']
)


8. КАК ОБЕЗОПАСИТЬ

Запускать от не-root пользователя:
docker run -u 1000:1000 -v /var/run/docker.sock:/var/run/docker.sock docker-manager

Ограничить capabilities:
docker run --cap-drop=ALL --cap-add=CHOWN --security-opt=no-new-privileges -v /var/run/docker.sock:/var/run/docker.sock docker-manager

Примечание: монтировать только для чтения (:ro) не подойдет, т.к. клиент должен писать в сокет


9. АЛЬТЕРНАТИВЫ ДЛЯ БЕЗОПАСНОСТИ

Если нужно ограничить доступ:

1. Docker API over TCP с TLS - вместо сокета использовать защищенный сетевой доступ
2. Docker Scout / AuthZ плагины - ограничить права через плагины авторизации
3. Свой скрипт-прослойка - запускать на хосте ограниченный скрипт, который принимает команды от контейнера


10. ИТОГ

Монтирование /var/run/docker.sock - это стандартный и самый простой способ дать контейнеру управлять Docker на хосте. Это как если бы вы дали контейнеру ключи от всей системы. Удобно для инструментов вроде Portainer, Jenkins, CI/CD агентов, но требует осторожности.
